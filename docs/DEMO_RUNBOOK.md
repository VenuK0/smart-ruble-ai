# Сценарий демонстрации SmartRubleAI v0.2.0-rc.1 (5 минут)

Исследовательский прототип. **Ни одна операция в нем не переводит цифровые рубли**. Данные синтетические. При оценке жюри разделять работающие функции, концепцию и будущие интеграции.

## Подготовка

На компьютере с Python 3.11+:

1. git clone https://github.com/VenuK0/smart-ruble-ai.git
2. cd smart-ruble-ai
3. python -m venv .venv
4. Windows: .venv\Scripts\activate
5. Linux/macOS: source .venv/bin/activate
6. python -m pip install -r requirements-dev.txt
7. python -m unittest discover -s tests -v
8. python -m uvicorn smartruble.api:app --app-dir src --host 127.0.0.1 --port 8000
9. Открыть http://127.0.0.1:8000/demo (резерв: http://127.0.0.1:8000/docs)

Сервис хранит операции в памяти. После перезапуска контракты и история очищаются. Для новой демонстрации можно создать другой идентификатор сметы (кнопка «Пример»).

## Пример выступления

- 0:00–0:40. Проблема: отчеты по целевым средствам обычно проверяют после совершения расходов. Показать AS IS.
- 0:40–1:20. Идея: проверка состава корзины до списания по статьям сметы. Показать TO BE и оговорить, что реальная интеграция еще не создана.
- 1:20–2:10. Открыть /demo, создать смету. Показать лимиты.
- 2:10–3:00. Проверить пример чека (Arduino + шоколад). Показать APPROVE/REJECT/REVIEW и разделение суммы на условно целевую и личную.
- 3:00–3:35. Открыть журнал. Продемонстрировать цепочку SHA-256 и то, что повтор того же ID не дублирует списание.
- 3:35–4:05. Запустить антифрод на заранее сгенерированных данных. Пояснить, что это отдельный эксперимент, пока не встроенный в основной поток платежа.
- 4:05–4:40. Рассчитать три сценария экономического эффекта, особо подчеркнув, что они основаны на предположениях.
- 4:40–5:00. Ограничения, дальнейшие шаги, финальная ценность продукта.

## Вопросы, которые стоит отрепетировать

**Почему классификатор показывает около 45% на ранее не встречавшихся товарах?**
Текущий метод TF-IDF + логистическая регрессия видит ограниченное количество синтетических названий. Мы измеряем обобщение на новые типы, поэтому результат существенно хуже, чем на похожих обучающих примерах. Низкая уверенность направляет позицию на ручную проверку. Следующий этап — новые данные и сравнение моделей.

**Почему при пороге 0,8 не все ответы верны?**
Порог относится к оценке уверенности модели, а не к вероятности безошибочного решения. Калибровка и внешняя валидация отсутствуют.

**Это реальный цифровой рубль?**
Нет. Смарт-контракт и платежный процесс в прототипе моделируются. Интеграция возможна только при наличии согласованного доступа и нормативно-технических условий.

**Есть ли реальные данные?**
Нет. Использованы синтетические товары и искусственно заложенные аномальные паттерны. Нужна проверка на обезличенных данных пилота.

**Сколько денег экономит система?**
Пока это неизвестно. Экономический модуль демонстрирует формулы и сценарии, а не фактические результаты организации.

**Можно ли развернуть систему для клиентов сейчас?**
Нет. Нужны авторизация, роли, БД, аудит безопасности, тестирование параллельных операций, интеграция и юридическая проверка.
